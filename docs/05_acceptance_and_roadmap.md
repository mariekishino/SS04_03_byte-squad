## コアの検証ケース

| ケース | 期待結果 |
| --- | --- |
| 空バイト列 | RLEは空、復元も空 |
| `A` | `(1,A)`、本体2 B |
| `AAAAAABBBBCC` | `(6,A) (4,B) (2,C)`、本体6 B |
| `ABCDEF` | 6組、本体12 B、元データより6 B増加 |
| `AAAABB` | 最後の`(2,B)`も出力する |
| Aを255個 | `(255,A)` |
| Aを256個 | `(255,A) (1,A)` |
| 同じ値の隣接する合法な組 | 拒否せず正しく復元する |
| 奇数長のRLE本体 | 理由付きのエラー |
| 個数0 | 理由付きのエラー |
| 復元上限を超える本体 | 大量出力を作る前にエラー |
| `[1,6,65,4,66,2,67]` | RLE方式、合計7 B、元12 Bへ復元 |
| `[0,65,66]` | 無圧縮方式、`AB`へ復元 |
| 方式情報ありで空パケット | エラー |
| `[0]`、`[1]` | 空出力への合法パケット |
| 未知の方式バイト | エラー |

複数のバイト列で `decode(encode(input))` が元と完全一致することを確認する。トレースの最終結果も通常の変換結果と一致させる。空入力の割合表示はNaNやInfinityにならないことを確認する。

## 画面での重要な検証

1. ミッション1を次へで最後まで進み、6 Bから元12 Bを復元できる。前へで以前の状態が正確に戻る。
2. ミッション2でAを2個ずつに分けると合法だが予算を超える。取消して3組にまとめれば成功する。
3. ミッション3でRLEを選ぶと「内容一致・容量超過」。無圧縮へ変えると成功する。
4. ミッション4で`(4,A)`だけを送るとBが2個不足する。`(2,B)`を追加すると成功する。
5. ミッション5で本体6 Bと合計7 Bが別々に示され、7 B上限で成功する。
6. 自動再生中に方式やミッションを変えても、旧トレースが新画面を更新しない。
7. 自由実験で対象外文字を入力すると、黙って削除・変換せず理由を示す。
8. ミッション2を照準・符号化の操作で完了できる。照準が同じ値の連続範囲を越えず、編隊の順番が保存される。
9. reduced-motion設定でも全工程を追え、演出中のリセットや画面移動で古い結果が再出現しない。
10. 復元中に元の編隊を参照しても、それが受信済みデータとして容量や一致判定に混入しない。

コアの正確性には自動テストを使う。画面は上記の代表フローをブラウザで確認する。利用可能なら既存のE2E環境を使ってよいが、低リスクの見た目だけの変更に大量のテストを追加しない。実行できなかった検証を実行済みと報告しない。

## 拡張ロードマップ：MVP完了後

### Phase 2：実ファイルとして保存・読み込み

圧縮したデータを独自の学習用ファイルへ保存し、読み込み直して復元・ダウンロードする。ここで「画面の表現」と「実際のバイト」をつなぐ。

- 保存形式には識別子、バージョン、方式、元サイズ等を定義する。
- MVPの1バイト方式情報だけを、本格的な保存形式として流用しない。
- バイト数をファイルの実サイズと照合する。
- 入力／復元サイズ上限、形式検証、破損時の挙動を先に決める。
- 任意ファイルに対する大きなトレースは、サンプル表示や差分記録へ変更する。

### Phase 3：別の圧縮方式を比較

`ABCABCABC`などで、過去の並びを参照する方式を教材として導入する。次に頻出記号へ短いビット列を割り当てる考え方を扱う。ビット数、参照情報、辞書等の追加容量を含めて比較する。

### Phase 4：アーカイブとZIP

複数ファイルの内容・名前・フォルダ構造をまとめ、取り出す体験を作る。本物のZIP作成・展開には既存の適切なライブラリを使う。

- アーカイブの一覧と、各ファイルの圧縮前後のサイズを表示する。
- ライブラリが内部トレースを提供しない場合は、実ZIP処理と教育用モデルの可視化を明確に分ける。
- 展開時の総サイズ・件数の上限を設け、危険なパスは拒否する。
- アーカイブに含まれるHTMLやスクリプトを実行する形でプレビューしない。

各Phaseは次の実装候補であり、MVPの受け入れ条件には含めない。
