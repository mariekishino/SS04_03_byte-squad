## コアの検証ケース

| ケース | 期待結果 |
| --- | --- |
| 空バイト列 | RLEは空、復元も空 |
| `A` | `(1,A)`、本体2 B |
| `AAAAAABBBBCC` | `(6,A) (4,B) (2,C)`、本体6 B |
| `ABCDEF` | 6組、本体12 B、元データより6 B増加 |
| `AAAABB` | 最後の`(2,B)`も出力する |
| Aを255個 | `(255,A)` |
| Aを256個 | `(255,A) (1,A)` |
| 同じ値の隣接する合法な組 | 拒否せず正しく復元する |
| 奇数長のRLE本体 | 理由付きのエラー |
| 個数0 | 理由付きのエラー |
| 復元上限を超える本体 | 大量出力を作る前にエラー |
| `[1,6,65,4,66,2,67]` | RLE方式、合計7 B、元12 Bへ復元 |
| `[0,65,66]` | 無圧縮方式、`AB`へ復元 |
| 方式情報ありで空パケット | エラー |
| `[0]`、`[1]` | 空出力への合法パケット |
| 未知の方式バイト | エラー |

複数のバイト列で `decode(encode(input))` が元と完全一致することを確認する。トレースの最終結果も通常の変換結果と一致させる。空入力の割合表示はNaNやInfinityにならないことを確認する。

## 画面での重要な検証

1. ホームを開くだけでは再生が始まらず、説明から「何を作るか」「容量と完全復元の2条件」が分かる。2つの入口が区別できる。
2. チュートリアル（旧ミッション1）を最後まで進め、6 Bから元12 Bへ復元できる。前へで以前の状態へ戻れ、完了してもゲームのクリア件数は増えない。
3. チュートリアル未完了の新しいセッションからゲーム任務1へ直接入れる。元データは固定され、個数・文字を自分で入力できる。
4. 任務1で`(2,A) (2,A) (2,B) (4,C)`を作ると内容一致・容量8 Bで超過。取消・編集で`(4,A) (2,B) (4,C)`にすると6 Bで成功する。
5. 任務1で`(4,B) (2,B) (4,C)`を送ると最初の文字が違う。`(4,A)`だけなら位置4以降が不足し、`(4,A) (2,B) (5,C)`なら位置10に余分なCがある。いずれも入力時に答えへ修正されず、実際の復元結果から直せる。
6. 個数0・256・小数・空欄、文字の小文字・複数文字・対象外文字を入力した場合は説明を出す。確定前の入力は送信へ混入しない。合法な組でも復元上限4096 Bを超える場合は出力確保前にエラーとなる。
7. 任務2で`ABCDEF`をRLEの6組として送ると内容一致・容量超過。無圧縮へ変えると6 Bで成功する。
8. 任務3でfixtureの`(4,A)`だけを送るとBが2個不足する。`(2,B)`を追加すると4 Bで成功する。
9. 任務4で本体6 Bと方式情報込み7 Bが別々に示され、7 B上限で成功する。
10. 自動再生中のモード・方式・任務変更、リセット、編集開始で旧トレースが新画面を更新しない。誤答から編集に戻っても組列は保持される。
11. ゲームで自動圧縮の全ステップ観察を強制されない。「結果を見る」は実際の復元トレースの末尾へ進み、前へ戻って復元過程も確認できる。
12. ヒントが段階的に表示され、豆知識・用語カードも開閉できる。開く操作で停止し、閉じても入力と再生位置が維持される。ヒント利用で減点しない。
13. 個数入力・文字入力・＋／−・文字選択・追加・編集・取消・送信をキーボードとタッチで操作できる。入力欄の左右キーやSpaceをゲーム用ショートカットが奪わない。
14. reduced-motionでも全工程を追える。狭い画面で主要操作を使え、補足パネルは下へ移る。
15. 比較用の元編隊は受信データや容量に混入しない。自由実験の元データ入力とゲームの回答入力も混同しない。

コアの正確性には自動テストを使う。画面は上記の代表フローをブラウザで確認する。利用可能なら既存のE2E環境を使ってよいが、低リスクの見た目だけの変更に大量のテストを追加しない。実行できなかった検証を実行済みと報告しない。

## 学習ロードマップ（合意済み）

学習順は **RLE → LZ77の考え方 → ハフマン → 組み合わせ → ZIP**。実装もこの順に進める。「今の方式ではうまく送れないデータに出会い、新しい工夫を獲得する」体験を軸にする。

以下のPhaseは学習章の段階を表す。現在の「ゲーム任務2：圧縮の逆効果」はPhase 1内の任務であり、Phase 2とは区別する。後続章は方針合意済み・未実装で、今回のMVP受け入れ条件には含めない。

### Phase 1：RLE章（現在のMVP）

チュートリアルとゲーム任務1～4、自由実験・用語を完成させる。

- 実装済み：チュートリアル、任務1～3、解説と歴史の読みもの。任務3では不足した末尾を直し、完全復元を確かめる。
- **次の実装：任務4「見えない1バイト」**。方式を伝える情報も容量へ含める。
- 自由実験・用語とMVPの受け入れ確認を行う。
- 章の終わりに`ABCABCABC`を見せ、同じ文字の連続以外にも規則があることを次章へつなぐ。

### Phase 2：LZ77の考え方 — 過去の並びを使う

観測記録に繰り返し現れる並びを、以前に出た位置と長さで表す。最初の教材候補は`ABCABCABC`。これは学習用モデルとし、本物のDEFLATE形式と区別する。

- プレイヤーは文字をそのまま送るか、既出の並びを参照するかを選ぶ。
- 受信側は、送信された情報と復元済みのデータだけから次の出力を作る。
- 参照情報にも容量が必要。元の文字数とトークン数だけを比べて「圧縮成功」としない。
- 実装前に、リテラルと参照の識別、距離・長さの範囲、重なりを許すか、記録サイズ、通信予算を仕様化する。短い教材で小さくならない場合も正しく表示する。
- 参照先の範囲外、復元上限、合法な誤答からの修正を検証する。

一区切りの条件：自分で送信表現を作り、実際に復元して比較・修正できる。「文字の連続」と「並びの繰り返し」の違いを説明できる。

### Phase 3：ハフマン — よく出る記号を短くする

頻出する通信記号に短いビット列を割り当てる体験へ進む。LZ77より先に発表された技術であることは、学習順と分けて年表で示す。

- 出現回数と符号の長さ、全体のビット数の関係を見せる。
- 符号を区切りなしで読み分けられる規則と、受信側での復元を扱う。
- 符号表を共有するか送信するかを明示する。送信する場合はその容量も計上する。
- バイトへ詰めたときの端数や付加情報も区別し、ビット数をそのままバイト数として表示しない。
- 教材の頻度分布、符号表の作り方をどこまで手動にするか、容量・成功条件は章の実装前に定める。

一区切りの条件：頻出記号を短くする効果と、復元規則が必要な理由を操作から理解できる。

### Phase 4：工夫の組み合わせ — DEFLATEへの橋渡し

LZ77の並びの参照とハフマンの符号化を組み合わせる考え方を学ぶ。

- 元データ、並びの参照への変換、ビット列、復元の逆順を対応させる。
- それぞれが何を短くするかを振り返る。組み合わせても常に小さくなるとは説明しない。
- 教育用の簡略モデルと、実際のDEFLATEの仕様・サイズは明示して分ける。
- 実DEFLATEを体験させる場合は適切なライブラリを使い、教育用のステップをそのライブラリの内部処理として表示しない。

一区切りの条件：二つの工夫の役割が分かり、ZIPの中で使える圧縮方式の一つへつながる。

### Phase 5：実ファイル、アーカイブとZIP — 観測記録を届ける

画面上のバイト列と実ファイルを結び、複数の観測記録を名前・フォルダ構造と一緒にまとめ、地球で取り出す。本物のZIP作成・展開には既存の適切なライブラリを使う。

- まず小さな教材ファイルの保存・読み込み・復元を確認し、画面上のバイト数とファイルの実サイズを照合する。
- 独自の学習用保存形式が必要なら識別子、バージョン、方式、元サイズ等を定義する。MVPの1バイト方式情報だけを本格的な保存形式として流用しない。
- ZIPはファイルをまとめる形式として扱い、中身の圧縮方式と区別する。無圧縮での格納も比較できるようにする。
- 一覧には各ファイルの圧縮前後のサイズとアーカイブ全体のサイズを表示し、名前などの管理情報にも容量が必要なことを示す。
- 実際に取り出したファイルが元と一致することを確認する。
- 入力／展開後の総サイズ・件数の上限、形式検証、破損時の挙動を先に決め、危険なパスは拒否する。
- 任意ファイルの大きなトレースは、サンプル表示や差分記録へ変更する。
- アーカイブに含まれるHTMLやスクリプトを実行する形でプレビューしない。

一区切りの条件：圧縮とアーカイブを区別でき、実ファイルをまとめて送り、地球で元どおり取り出せる。
