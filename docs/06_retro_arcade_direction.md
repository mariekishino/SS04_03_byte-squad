# 2Dレトロアーケード：ビジュアルと操作の仕様

## ユーザー指定と実装方針

ユーザーは、利用者がゲームとして遊べること、2Dでよいこと、インベーダーゲームや1980〜90年代のASCII調の見た目を希望している。

本資料では、それを「整列したデータ編隊＋画面下の自機＋端末風の文字と枠」に具体化する。2DアーケードとASCII端末の要素を組み合わせた創作デザインとし、厳密な年代再現や実在ゲームの複製は目的にしない。ゲーム内タイトルの案はBYTE SQUAD、日本語副題は「宇宙通信士の圧縮ラボ」。タイトルは仮称でよい。

## 画面を開いたときの印象

- 黒に近い背景、少数の明るい色、くっきりした四角い輪郭。
- 大きな等幅英字のタイトルと02の目的説明。その下に「チュートリアル：通信の練習」「ゲーム：通信任務に挑戦」の入口を置き、違いを日本語で添える。
- メイン画面は大きな一つのプレイフィールド。上に整列した編隊、中央に符号化カプセル、下に自機。
- プレイ画面の上端にTUTORIALまたはゲーム任務番号、MODE、BYTES、LIMIT。下端に操作キーと短い通信ログ。
- ゲーム任務選択は番号付きSTAGE一覧、成功はSTAGE CLEAR、失敗はRETRY。チュートリアル完了はTRAINING COMPLETEと表示する。
- ホームでは目的説明を省略しない。プレイ中はその操作に必要な1文を出し、段階的ヒントと豆知識・詳しい用語はサイドバーで開閉できる。

## データと見た目の対応

| 圧縮上の意味 | ゲーム表現 | 誤解を避ける条件 |
| --- | --- | --- |
| 入力の1バイト | 値A～Zが読める1機のデータ機 | 文字・論理位置が識別できる |
| 同じ値の連続 | 横に並んだ同種の編隊 | 離れた同じ値を勝手に集めない |
| 読み取り位置 | 自機から伸びるスキャン／照準 | ステップ記録の位置と一致する |
| RLEの組 | COUNTとVALUEの2マスのカプセル | 1組は2 B。カプセル1個＝1 Bではない |
| 無圧縮 | データ機をそのまま通信レーンへ送る | 元のバイト数を維持する |
| 方式情報 | 先頭のMODE用1マス | ゲーム任務4（旧ミッション5）等では1 B加算する |
| 復元 | カプセルから指定数のデータ機が出現する | 受信データから実際に生成する |
| 不一致 | 不足位置の枠、違う値のラベル、余分な機体 | 元の編隊と受信編隊を混同しない |

元データは左から右、上から下に読む。同じ値でも離れた位置にあるものは連続として扱わない。折り返した行をまたぐ連続は論理インデックスで扱い、選択中の範囲を両行に示す。

## 通信の目的と操作の手応え

プレイフィールドには送信元「宇宙船」と受信先「地球」を明記する。地球は小さなドット風の図形とラベルで表現してよい。圧縮中は宇宙船側、復元中は地球側の処理であることを表示し、同じフィールドの表示が切り替わっても現在地を見失わないようにする。

チュートリアルで組を確定したときは、対応する編隊・生成された2マス・更新された本体サイズを同時に強調する。ゲームでは入力した個数・文字と生成された2マス・本体サイズを対応付け、元編隊を正しく表しているかは送信後の比較で示す。復元時は、読み取っている組とそこから出現したデータ機を対応付ける。チュートリアルのガイド中もこの対応を見せ、操作の結果を短い日本語ログで伝える。例：「Aを6機読み取り、個数と値の2 Bにまとめました」。手動入力では追加した組がすぐ分かるようにする。照準で元データの正しい連続数や文字を自動入力しない。

送信操作には通信レーンの反応を付け、復元・判定後に02の依頼に対応した地球からの応答を表示する。演出のために追加の待機や確認操作を要求しない。reduced-motion時もラベル・枠・数値によって同じ対応を確認できるようにする。

## 遊びの具体例

ゲーム任務1では、上部に`AAAABBCCCC`の10機が現れる。プレイヤーが個数「4」と文字「A」を入力して「組を追加」を押すと、中央にCOUNT=4とVALUE=Aの2マスが現れる。続けてBとCの組も自分で入力する。

組の追加ごとに通信レーンの使用量が2 B増える。`(4,A) (2,B) (4,C)`なら3組・6 Bで送信でき、地球で元の10機へ戻ってSTAGE CLEARになる。

一方、最初を`(3,A)`にすれば地球側のAが1機足りず、最初を`(4,B)`にすれば違う文字の編隊が現れる。間違いを入力時に消さず、元の編隊との最初の違いや不足・余分をラベルと枠で示し、組を編集して再送できるようにする。

元のデータを撃って失う操作にはしない。照準やビームは読み取り位置を伝える補助として使い、入力した組から何が復元されるかを中心に見せる。

## 操作

ショートカットはプレイフィールドにフォーカスがあるときだけ有効。input、textarea、select、通常のbuttonでの入力・標準操作は妨げない。フォーカス移動で操作から抜けられるようにする。

| 状態 | キー | 処理 |
| --- | --- | --- |
| 手動の組作成 | 左／右 | 個数の入力候補を1～255の範囲で減らす／増やす。元データの連続数には制限しない |
| 手動の組作成 | Space | 個数・文字が形式上正しければ、入力候補を1組として追加 |
| 手動の組作成 | Z | 最後に確定した組を取り消す |
| 圧縮・復元の観察 | 左／右 | 前のステップ／次のステップ |
| 圧縮・復元の観察 | Space | 自動再生／一時停止 |
| 送信可能な状態 | Enter | 送信シミュレーションを開始 |
| プレイ中 | Esc | 自動再生を一時停止 |

Spaceの意味が変わるため、現在の操作を画面下へ常に明記する。同じ処理を行う日本語ラベル付きボタンも置く。リセットは明示ボタンを使い、意図しないキー操作で全消去しない。

ゲーム任務3の修理も、共通の個数・文字の入力欄とボタン／選択欄で組を追加する。編隊を欠けたまま実際に復元し、修正前後を比べる流れを優先する。

## 美術ルール

| 項目 | 基本方針 |
| --- | --- |
| 背景 | 黒～非常に暗い紺。例：`#080C14` |
| 基本文字 | 明るい白。例：`#E8F0F2` |
| 主色 | 緑またはシアン。例：`#80FF9F`、`#72E4FF` |
| 注意・超過 | 黄系。例：`#FFD166` |
| 不一致 | 赤系＋記号・文言。例：`#FF7885` |
| 枠 | 1～2 pxの直線、角は四角。情報の区切りに使う |
| 欧文・数字 | 等幅フォント。見出しはピクセル風にしてよい |
| 日本語 | 読みやすいフォールバック。本文を無理に粗いドットへ変換しない |
| 機体 | シンプルな独自のドット絵／記号風SVG。値ラベルを大きく表示 |
| 装飾 | 少量の星、区切り記号、任意の薄い走査線 |

ASCII調の記号や文字はブラウザの要素として描画してよい。文字だけで大きな一枚絵を組むことは要件ではない。3D、立体的な陰影、大量のグラデーション、カード中心の管理画面の構成は使わない。説明パネルも端末風の簡潔な枠にする。

## 演出と状態の同期

- スキャン、組の確定、送信、1バイトの復元、成功に短い反応を付ける。
- 目安150～300 ms。圧縮の学習ステップ自体は既存仕様の1秒間隔を基本とする。
- アニメーションの終了を圧縮結果の確定条件にしない。コアの状態から描画し、演出を省いても同じ結果になる。
- 入力変更、戻る、リセット、画面移動時は古い演出を止める。タイマーや演出完了コールバックから古いデータを書き戻さない。
- 元編隊の薄い表示は「比較用の元データ」と表示する。送信バイト数へ二重加算しない。
- 走査線は任意。点滅、敵の強制降下、画面揺れ、過剰な発光は使わない。
- reduced-motion時は移動を即時の状態切替へ置き換える。操作と学習内容は同じ。
- サウンドは初回必須ではない。後で加えるなら初期ミュート・明示ONとし、成功や失敗を音だけで伝えない。

## 学習ゲームとしての優先順位

チュートリアルでは圧縮・復元の観察、ゲームでは自分で表現を作り、送って結果を見て直せることを最優先にする。自機や編隊はその操作を面白く見せるために使う。

反射神経、狙撃の精度、残機、迫る敵への対応はMVPの課題にしない。後でアクションモードを作る場合も、ステップ観察できる学習モードを保持する。

## エージェントの確認項目

1. ホームで通信の目的と成功条件が伝わり、練習とゲームの入口を区別できるか。
2. 自機・照準・カプセルが実際の操作に対応し、ゲームでは個数と文字を自分で決められるか。
3. 1機1 B、RLEの1組2 B、方式情報1 Bを区別できるか。
4. 数値と日本語を無理なく読めるか。
5. 演出を止めても処理の状態と正しさを確認できるか。
